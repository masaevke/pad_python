# Генератор pg2core

Утилита создавалась для задач миграции с хранилища ADWH на MSSQL в ADB на
Greenplum. В рамках этой миграции она помогает подготовить загрузку
PostgreSQL-источников и модели нового хранилища: читает метаданные таблиц,
проверяет структуру и генерирует raw-DDL, dbt-модели prep/core/view,
YAML-описания и JSON-конфигурации потоков Dataflow.

На вход подаются метаданные PostgreSQL: из каталога БД или из JSON-файла.
Результат сохраняется в локальный каталог. 

## Установка

Нужен Python 3.10 или новее. Команды ниже выполняются из папки `avtomat`.

```bash
python -m venv .venv
```

Активация окружения в Git Bash на Windows:

```bash
source .venv/Scripts/activate
```

В PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Установка проекта вместе с зависимостями:

```bash
python -m pip install -e .
pg2core --help
```

Режим `-e` связывает установленный пакет с исходниками: изменения
`pg2core_generator.py` доступны без переустановки. Обычная установка
`python -m pip install .` также поддерживается.

## Настройка и запуск

Параметры таблиц, схем и моделей задаются в словаре `config` внутри
`pg2core_generator.py`. Их можно переопределить JSON-файлом через `--config`.
При обычной установке используйте этот флаг, чтобы передать свои настройки.

При установке с `-e` скопируйте `.env.example` в `.env` рядом с исходным
скриптом и заполните данные для нужных подключений. Также поддерживаются
переменные окружения: их значения имеют приоритет над `.env`.
При обычной установке модуль находится в `site-packages`, и `.env` из папки
проекта автоматически не читается; передавайте секреты через переменные
окружения.

После заполнения конфигурации можно сформировать локальный план:

```bash
pg2core --dry-run
```

`--dry-run` отключает применение DDL и создание потоков через API. Если
`metadata_file` не задан, чтение метаданных всё равно требует подключения
к PostgreSQL. Флаг `--metadata` позволяет передать JSON-метаданные и
сформировать план без подключения к PostgreSQL.

Команда `pg2core` использует тот же обработчик, что и
`python pg2core_generator.py`. Все параметры перечислены в `pg2core --help`.

Создание объектов ADB и потоков Dataflow включается отдельно флагами
`--apply-ddl` и `--create-flows`. Для этого нужны доступ к соответствующим
сервисам и заранее созданные схемы. Сгенерированные dbt-модели используют
макросы целевого dbt-проекта; их перенос и `dbt build` выполняются отдельно.

## Демонстрационный запуск без БД

В папке `examples` находится искусственный пример схемы продаж для подготовки
нового контура ADB в рамках миграции ADWH → ADB:

- [`config.json`](examples/config.json) задаёт таблицы, схемы ADB, параметры
  dbt и каталог результата. Создание объектов БД и потоков API отключено.
- [`metadata.json`](examples/metadata.json) заменяет чтение структуры
  PostgreSQL: содержит описания колонок, их типы и первичные ключи.
  Строки бизнес-данных в этом файле не хранятся.

В примере три таблицы:

| Таблица | Назначение | Первичный ключ |
| --- | --- | --- |
| `customers` | Покупатели | `customer_id` |
| `orders` | Заказы | `order_id` |
| `order_items` | Позиции заказов | `order_id`, `line_number` |

После установки проекта выполните из папки `avtomat`:

```bash
pg2core --config examples/config.json --metadata examples/metadata.json --dry-run
```

Для этой команды не нужны `.env`, PostgreSQL, ADB или доступ к Dataflow.
Все относительные пути отсчитываются от текущей папки запуска.
Дата начала партиций в конфигурации зафиксирована, поэтому SQL не зависит
от дня запуска.

При успешном выполнении программа завершится с кодом `0` и сохранит результат
в `pg2core_output/demo/`:

| Файл или каталог | Содержимое |
| --- | --- |
| `raw.sql` | DDL трёх raw-таблиц Greenplum |
| `raw_comments.sql` | Комментарии raw-таблиц |
| `metadata.json` | Метаданные после нормализации типов |
| `selectors.proposed.yml` | Предлагаемые селекторы dbt |
| `project/models/sales/prep_sales/` | Три prep-модели и их свойства в `properties/` |
| `project/models/sales/core_sales/` | Три core-модели, три view-модели и их свойства |
| `project/sources/sales/` | Три описания источников dbt |
| `project/docs/sales/` | Документация таблиц и колонок |
| `execution_*.json` | Отчёт о выполнении; последний шаг — `complete` со статусом `ok` |

Генерация потоков в демо отключена, поэтому каталог `flows/` не создаётся.
Результат демонстрирует подготовку файлов; выполнение SQL и `dbt build`
в этой команде не запускается. Каталог `pg2core_output/` исключён из Git.

Повторный запуск с теми же настройками разрешён и создаёт новый отчёт
`execution_*.json`. Если вы изменили пример и получили сообщение о другом
существующем плане, задайте новый каталог результата:

```bash
pg2core --config examples/config.json --metadata examples/metadata.json --dry-run --output pg2core_output/demo_v2
```

## Аннотации типов и mypy

В проекте используются аннотации параметров и результата,
типизированные коллекции `list[T]` и `dict[K, V]`, `T | None`,
классы данных `dataclass` и проверки возможного `None`.

В `pg2core_types.py` описаны настройки (`Config`), колонки (`ColumnMetadata`),
метаданные таблиц (`TableMetadata`), переопределения (`TableOverride`)
и подготовленная таблица (`TablePlan`). Например, поле `primary_key`
содержит `list[str]`, а необязательная дата `partition_start` имеет тип
`str | None`. Изменяемые значения по умолчанию задаются через
`field(default_factory=...)`.

Аннотация `Iterator[PgConnection]` описывает генератор контекстного менеджера:
он выдаёт соединение через `yield`, а после выхода из `with` закрывает его.

Исходный словарь `config` и формат демонстрационных JSON-файлов сохраняются.
На входе словари преобразуются в классы данных; внутри генератора поля
читаются как `cfg.pg_database` и `table.columns`. Для записи JSON
колонки преобразуются обратно в словари через `asdict`.

При вызове из Python внутренние функции теперь принимают эти классы данных:
для подготовки аргументов из словарей служат `config_from_dict()`
и `metadata_from_dict()`. Параметры командной строки остаются прежними.

Для неоднородных входных JSON-словарей и форматов API/YAML применяется
дополнительный тип `Any`: структура этих значений определяется внешним
форматом. Внутренние настройки, таблицы и колонки имеют конкретные типы.
`mypy` проверяет согласованность типов в коде без его запуска. Аннотации
и `dataclass` сами по себе не проверяют тип каждого значения из JSON:
проверки имён, ключей и поддерживаемых типов данных выполняются при запуске.

Установите зависимости для разработки в активированное окружение
и запустите проверку из папки `avtomat`:

```bash
python -m pip install -e ".[dev]"
python -m mypy
```

Дополнение `[dev]` устанавливает `mypy` и описания типов (`types-*`)
для `requests`, `psycopg2` и `PyYAML`. Настройки проверки находятся
в `pyproject.toml`: проверяются оба Python-модуля, включён `strict = true`,
целевая версия Python — 3.10. Ожидаемый результат:

```text
Success: no issues found in 2 source files
```

После изменения типов можно повторить демонстрационный запуск из предыдущего
раздела, чтобы проверить работу программы на примере.

## Ошибки метаданных

Если таблица из `pg_tables_to_convert` отсутствует в метаданных, генератор
вызывает собственное исключение `MetadataValidationError`. Командная строка
перехватывает его, выводит сообщение `Ошибка метаданных: Метаданные таблицы
не найдены: <имя таблицы>` и завершает работу с кодом `1`.

В этом случае проверьте список `pg_tables_to_convert` и содержимое JSON-файла,
переданного через `--metadata`. План при такой ошибке на диск не сохраняется.
